# Changelog

All notable changes to `agent-memory-sync` are recorded here. This is a
private, internal-only tool (not published to npm; see `package.json`), so
there is no semver release process to anchor entries to — each entry below
is dated instead. The format is loosely based on
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Security

- **`profiles/*.json` no longer commits a real operator's machine paths, OS user name or Claude Code workspace slug.** Only `profiles/mac-mini.example.json`, `profiles/macbook.example.json` and `profiles/linux.example.json` (placeholder templates) are tracked now; a machine's real, filled-in profile (`profiles/mac-mini.json`, `profiles/macbook.json`, `profiles/linux.json`, or any further machine's) is local-only, ignored by a new `packages/agent-memory-sync/.gitignore` rule (`profiles/*.json` with a `!profiles/*.example.json` exception). The running `watch`/periodic-sync launchd or systemd unit on an existing machine needs no configuration change, since it already resolves the same absolute `--config`/`AGENT_MEMORY_SYNC_CONFIG` path either way; see `docs/machine-setup.md`'s "Real per-machine profiles are local-only" section for the setup and migration steps, including the one-time backup/restore a machine with an already-committed real profile needs around its next `git pull`. That backup/restore step has a narrow window where the profile file is briefly gone from disk (between the pull and the copy-back); `run`, `watch` and `restore` (every command that actually syncs) now refuse an explicitly-named `--config`/`AGENT_MEMORY_SYNC_CONFIG` path that does not exist with a clear `CliError` naming the missing path (exit `3`), instead of silently falling back to `{}` and only failing later, less clearly, once `remoteUrl` turns out unset. `config show`/`config get`/`config set` are unaffected: inspecting or creating a not-yet-configured machine's config file is still expected to work against a path that does not exist yet. See `docs/machine-setup.md`'s "Behavior during the removal window itself" note for the full recommendation (stop the periodic job and pause `watch` before pulling).

### Fixed

- **The held-back note for an adopted path no longer names a snapshot copy that does not exist.** After `--accept-mass-delete`, when a real run's pre-apply snapshot holds no copy of a held-back path (the path had no local copy when the adoption ran), the note says so and prints no copy step and no restore fallback; the notes for a snapshotted path and for a dry run are unchanged (500b0ecf follow-up b74a7903).
- **A sync no longer spreads conflict markers or republishes stale files through the hub.** Three behaviours together close one incident class, in which unresolved markers or a stale local copy reached the hub and then other machines:
  - A push never publishes conflict markers. A path whose local content carries markers, or whose three-way merge against the hub could only produce them, is held back by `run --mode push`, `run --mode sync` and a watch tick: the hub keeps its content for it, the path is counted in `conflicts=N` and named in a note, and its base entry stays as it was, so it is held back again until the local file is resolved. A `local-wins` or `remote-wins` strategy that resolves to marker-free content still publishes. The held-back note names the next step for its reason (pull or sync first, resolve the markers, repair the hub copy, a local deletion that was not published, or the one snapshotted file to copy back after an accepted mass deletion), and a watch tick that holds paths back logs how many and which. The exit code of a conflict is unchanged (`0`).
  - A hub file that itself carries conflict markers is never merged into, on either side. `pull` leaves the local file byte-identical and `push` skips the path whatever the local copy or the strategy says, so a `local-wins` edit no longer overwrites a markered hub file; the path is reported and its base entry is kept. An ownerScoped peer file keeps its mirror rule and is flagged.
  - After a successful push the base snapshot advances per path, to the hub content only where the local copy equals it (otherwise the previous entry is kept, or none), instead of being replaced by the whole hub tree. A second push without a pull in between no longer republishes a stale local copy over a peer's newer version, nor deletes a hub-only file this machine never pulled. Queued snapshots replayed in one push chain the base, so a file edited, created, reverted or deleted again while the remote was unreachable ends at its final state. Paths no sync path maps are still dropped from the base write, and the owner-scoped filter stays on the read side so a peer's deletion of its own file still propagates.
  - The mass-delete guard measures a queued replay's deletions net of the run (a file created and then removed again while offline does not count), and under `--accept-mass-delete` the final base write no longer records a replayed edit of an adopted-deleted path.

  Documented in the README ("What a push publishes, and conflicts", including the recovery steps for a hub that already holds a markered or regressed file) and in `docs/sync-behavior.md`.

- The temp-clone race test now checks that its eager global git config is in effect (`git config --global --get gc.auto` returns 1) and skips with a message naming the git >= 2.32 requirement otherwise, instead of passing without exercising the race (task d8f23d38).

- **A recursive remove of a pull/push/restore temp clone could fail with `ENOTEMPTY: directory not empty, rmdir .../tmp/pull/.git/objects`, a rare flake in `tests/integration/pull-guard.test.ts` on CI** (agent-tasks 14d04351). `git fetch` and `git commit` end by spawning `git maintenance run --auto --detach`, a daemonised process that outlives the git command, takes `.git/objects/maintenance.lock`, and, when git decides a gc is due, repacks and prunes inside `.git/objects`; `StateStore.clearTemp` and the next run's `createTempRepoDir` remove the temp clone recursively, and a remove that walks `objects/` while that process writes into it fails with `ENOTEMPTY`. `GitClient.prepareWorkingCopy` (`src/memory-sync/git-client.ts`) now sets `gc.auto=0` and `maintenance.auto=false` in the temp clone's own config right after `git init`, so no background git process is ever started in a clone this tool deletes (the clone is disposable, so the housekeeping has no value there). The setting lives in the repository config rather than in `-c` arguments or the environment, so it reaches the detached child and leaves the argv a custom `gitBinary` wrapper sees unchanged. `tests/unit/git-client-temp-clone-cleanup.test.ts` forces the race on demand (a global git config with `gc.auto=1`, loose fetched objects, and blobs in `objects/17`) and removes 15 fresh temp clones right after `prepareWorkingCopy`; without the fix every removal failed with `ENOTEMPTY` (15 of 15 with the fix reverted; 30 of 30 in each of three runs of an earlier 30-iteration version), with it none does. The flake itself did not reproduce locally, so the trigger on CI is inferred: with default thresholds the daemon only takes and releases the lock, which a loaded runner can schedule late enough to land inside the remove.

- **`watch` now delivers every syncPath that is missing at start once it appears: several missing paths under one directory, a nested path whose parent is missing too, and a path created before its watch could be opened** (agent-tasks d09a0d3a; follows the ready-line gate of 50a13ffe below, whose "Limits" paragraph and the two startup warnings it describes no longer apply). chokidar 4.0.3 lost these three shapes however `watch` waited for it: the targets under one directory shared that directory's single fs.watch and only the first registered listener's target was delivered (`handler.js`, `setFsWatchListener`, `fsWatchBroadcast`, `_handleRead`), a nested target was re-added for its leaf name and never matched, and a target created before chokidar's deferred step skipped the directory's initial read (`_handleDir`). Operator decision: per-target arming. `watch` now hands chokidar only the syncPaths that exist at start, so chokidar's `ready` and the ready line mean what they say (chokidar's double `ready` and its `ready` before an existing path's own watch cannot happen for a missing path any more). Each missing syncPath gets its own tracker that checks that one path every 250 ms, with the first check at once, before the ready line; when the path exists it gets its own chokidar watcher, and after that watcher's `ready` the path is read once and every file found is reported as a change, which also covers a write in the first milliseconds after an fs.watch is opened on macOS. No directories are created and chokidar stays at 4.0.3. Removed with the gate: the `could not confirm the watch on <paths>` warning and the two startup warnings for shared and nested missing paths. The ready line now also waits for the operating system watch to be live (`confirmWatchLive` in `src/commands/watch-arming.ts`): after chokidar's `ready`, `watch` opens a watch on a scratch directory in the OS temp directory and writes into it until an event arrives (nothing is written into a syncPath), because of what was measured on macOS with Node 26 (100 trials each, a scratch file and directory in the OS temp directory): a write made synchronously right after `fs.watch(file)` returned was missed 100 of 100 times, one made after a single `setImmediate` 0 of 100, and for `fs.watch(dir)` an immediate write was missed at most 2 of 100 times. On macOS a file watch is kqueue-backed and is not live until the event loop has polled once; waiting for an event on a scratch watch guarantees at least that poll after the sync paths' watches were opened. That libuv serves all watches of a process from one stream, so that a later watch shows an earlier one to be live, is not verified. The argument covers kqueue file watches only: a directory watch also missed a write made after one `setImmediate` in about 1 of 100 to 200 trials, so for a directory syncPath a write right after the ready line can still be missed rarely. Without it the ready line came out immediately after the watch on an existing syncPath opened, and an edit right after it was lost far more often than before this change, where the old gate had added a few milliseconds there (measured below). `AGENT_MEMORY_SYNC_WATCH_ARM_TIMEOUT_MS` (default 5000) now bounds this wait; on timeout `watch` warns `could not confirm within <N>ms that the operating system file watch is live` and prints the ready line anyway, and when the probe cannot be set up at all (scratch directory, watch or write fails) it warns `could not check that the operating system file watch is live (<cause>)` instead. A shutdown during the wait ends it at once, without the ready line or a warning. New with `--verbose`: `N syncPath(s) do not exist yet and are checked every 250ms: <paths>` at start, then `syncPath <path> appeared, watching it` and `syncPath <path> is armed (N existing file(s) reported)` per path. A path that is gone again when its watcher is about to be opened goes back to its tracker (`syncPath <path> disappeared again before it could be watched, waiting for it`); a path removed after that check is not re-armed. The bound on the appeared path's watcher no longer keeps the process alive during a shutdown. A path that is removed and created again after it appeared is not re-armed, the same as one that existed at start. `tests/integration/watch-ready-arming.test.ts` pins each shape (the shared and nested tests, and the early-created test with the injected delay of `tests/helpers/arming-delay-preload.cjs`) and fails on the previous code; `tests/unit/watch-arming.test.ts` covers the tracker and the re-read, and the integration tests also pin a missing syncPath of kind file, the three shutdown cases (during the live-watch confirmation, while an appeared path's watcher is not ready, while paths are missing) and the setup-failure warning. The test helper `trackWatchProcessGroup` puts the launcher-less shutdown test's process into the last-resort cleanup set of `tests/helpers/watch-process.ts`. Documented in `docs/cli-reference.md`.

  Measurement (interleaved A/B, base commit 6bbe14c against this change, 12 `yes` CPU hogs on a 12-core Mac plus unrelated ambient load, load average 15 to 30; one file-run is one whole `node --test` run of one integration test file with the default 120 s no-progress budget; four files: watch-teardown-guard and remote-unreachable-escalation 60 file-runs each, watch-restore and watch-mirror-delete 40 each, so n = 200 per tree). Stall messages ("showed no progress signal"): base 4 in 200 file-runs (3 in remote-unreachable-escalation, 1 in watch-mirror-delete), this change 0 in 200. Non-zero exits that are not stalls: base 2 (a 15 s fixed-deadline timeout in watch-restore and an EPERM in the watch-teardown-guard group-kill test), this change 1 (the same EPERM test). The stall class is therefore not proven fixed (0 of 200 against 4 of 200, Fisher exact two-sided p about 0.12), but it is no longer measurable at this n. The same A/B on the tree before the live-watch confirmation was added measured a regression: 11 stall messages in 8 of 23 file-runs against 0 in 23 for base, which is why the confirmation exists. Raw counts and logs are in the pandora run's evidence directory.

- **`watch` printed its "watching N path(s)" ready line before the watch for a missing syncPath existed, so a write right after it could be lost and the tick never started** (agent-tasks 50a13ffe, the "no progress signal" stall in `tests/helpers/watch-process.ts`). Superseded by the entry above (d09a0d3a): the wait on chokidar's `getWatched()` state, its `could not confirm the watch on <paths>` warning and the two startup warnings no longer exist, and the Limits paragraph below no longer applies; what follows is the history of that change. chokidar 4.0.3 counts a syncPath that does not exist at start as ready at once and opens the watch on its nearest existing ancestor only in a later asynchronous step, skipping that directory's initial read; a write inside the gap is never delivered afterwards. `watch` now waits after chokidar's `ready` until chokidar's own `getWatched()` state shows that ancestor watch (a bounded poll, `src/commands/watch-arming.ts`), and only then prints the ready line. The wait is bounded by 5000 ms (`AGENT_MEMORY_SYNC_WATCH_ARM_TIMEOUT_MS` overrides it): a path that cannot be confirmed in time produces a warning naming it and the ready line still prints, so startup never hangs. Nothing is written into the synced directories for this, and the chokidar version is unchanged. A syncPath that exists at start is unaffected. The stall was measured at 0 of 50 file-runs on ubuntu-latest CI and at 3 stall messages in 2 of 50 file-runs locally under 12 CPU hogs, all in tests that start with `logs/` absent; `tests/integration/watch-ready-arming.test.ts` pins the ordering by construction with an injected delay in the deferred step (`tests/helpers/arming-delay-preload.cjs`). The no-progress budget in `tests/helpers/watch-process.ts` is unchanged. Measurements and the residual are in the pull request.

  Superseded: the three shapes below are delivered now (see the entry above). Limits (chokidar 4.0.3, described in `src/commands/watch-arming.ts`): the gate proves that the anchor's watch exists, not that every missing path is delivered. For two or more missing syncPaths under one existing directory, only the target whose deferred listener registers first is delivered: the targets share the directory's single fs.watch, chokidar's `fsWatchBroadcast` calls their listeners in registration order, and the first `_handleRead` takes the directory's readdir throttle while the closing re-read reuses that first caller's target (`handler.js`, `setFsWatchListener`, `_handleRead`). Which target registers first is a stat/realpath race inside chokidar, with or without this change. A missing path whose parent is missing too, and a path created while the wait runs, are not delivered either. `watch` now prints one startup warning line when two or more distinct missing syncPaths share an existing directory (a path configured twice counts once), and one when a missing syncPath's parent is missing as well; the ready line does not guarantee delivery for those paths. Per-target gating is not part of this change. chokidar can emit `ready` twice when a syncPath is missing at start; `watch` handles it once, so the ready line and the could-not-confirm warning print at most once. The new environment variable and both warnings are documented in `docs/cli-reference.md`.

- **The checkout-reliability guard (exit `7`) missed a checkout that lost content without losing files.** `findUnreliableCheckout` (`src/memory-sync/guards.ts`) counted only paths the base snapshot tracks that came back missing on the working copy. A checkout that truncates every checked-out file to zero bytes in place, instead of removing it, walked straight past this check: every path is still "present". It now also counts a base-tracked path as unreliable when it is present but comes back at zero length while the base's own content for it was non-empty ("emptied"); a path that was already empty at base, or a remote rewrite to different but still non-empty content, is never counted. Lost and emptied paths are combined before either the absolute or the proportional threshold is applied, and the refusal message names both counts and the threshold. Found by review R2 (adversarial) of the 2026-09-11 wipe fix (pandora run `.ai/runs/2026-09-11-memory-sync-wipe`, D-013; agent-tasks 56e20494), reachability recorded as lower than the incident path since an `rm -rf` removes files rather than truncating them.
- **`--accept-mass-delete` bypassed the emptied-checkout refusal above.** `findRemoteDeletionsToAccept` (`src/memory-sync/accept-remote-deletions.ts`) only collected paths the remote reports as missing, so a finding whose files were present-but-emptied yielded no paths to adopt, `acceptRemoteDeletions` returned `null`, and every call site (`push.ts` real run and `--dry-run` preview, `pull.ts`) fell through to skipping the checkout guard entirely. Measured pre-fix against the truncating stub at 50 files: `push --accept-mass-delete` exited `0` and published 50 zero-byte files with no snapshot taken; `sync` and `pull` with the flag emptied the 50 local files too. `--accept-mass-delete` answers "the remote really did drop these files"; it does not answer "this checkout came back zeroed", and adopting an emptied checkout would copy and apply zero-byte content as if it were real. A new shared predicate, `assertOverridableCheckout` (`src/memory-sync/guards.ts`), throws `UnreliableCheckoutError` (exit `7`, unchanged) whenever the finding carries emptied paths, flag or no flag; `findRemoteDeletionsToAccept` and pull's override branch both route through it instead of each hand-writing the check, and the refusal message no longer recommends `--accept-mass-delete` when it would only refuse again. Found by review R1 (rigorous) of the emptied-checkout fix above (agent-tasks 56e20494).
- **A file name containing a literal backslash was published, pulled or restored under a mangled path.** `collectLocalSyncFiles`, `normalizeRemoteRelativePath`/`normalizeLocalRelativePath` (`src/memory-sync/config.ts`) and `GitClient.listFiles` (`src/memory-sync/git-client.ts`) converted every backslash to `/` unconditionally, on every platform. On darwin/linux a backslash in a name is not a path separator, so `logs/back\slash.md` was pushed as `shared/logs/back/slash.md`, a name `pull` and `restore --from-commit` can never map back to the original file. Backslash-to-`/` conversion now applies only on win32 (where it is exact). Two directions, two outcomes on darwin/linux: a **local** sync path (or an operator-typed `restore --path`) whose name carries a backslash refuses every command that collects local sync files (`push`, `sync`, `restore`, and `pull` too, since it merges against the remote) with exit `3`, naming the path, rather than publishing or restoring it mangled; a `watch` service exits `3` on every tick until it is renamed. A **hub-side** path a foreign writer committed with a backslash is skipped instead: `pull` reports it in the run's `notes` and still applies every other file, exit `0`; destination-form `restore --from-commit` reports its base-snapshot skip in the additive `notes` array of its JSON/YAML payload (including under `--quiet`), while restoring the backslash-named path itself to a local destination is still refused outright, before any file or pre-apply snapshot is written, since that is the local-mapping case. The `repositorySubdir` config value goes through the same check instead of an unconditional backslash-to-`/` rewrite (`src/config/loader.ts`). Found by review R5 of the 2026-09-11 wipe fix (pandora run `.ai/runs/2026-09-11-memory-sync-wipe`, agent-tasks 73ea60bf); pre-existing at `3060f69`, not reachable on the live hub.
- **A peer's ownerScoped file could never converge on `pull`.** A file inside an `ownerScoped` directory destination that is not this machine's own `<profile>.json` is now mirrored from the remote unconditionally instead of 3-way merged, and a local file left with stale inline conflict markers is now named in the run's `notes`. Incident record and diagnosis: pandora run `.ai/runs/2026-09-11-sync-peer-file-conflict` (agent-tasks e104c9f2).
- **The 2026-09-11 memory-corpus wipe.** A periodic `run --mode sync` tick and a `watch` tick shared one state directory with nothing serialising them. The watch tick's cleanup removed the sync tick's freshly checked out working copy under `stateDir/tmp` after git had already reported success, so the pull read an empty tree, resolved every path to a deletion and removed the local corpus (about 400 files) from disk; the follow-up push published the deletion, and the Linux peer mirrored it one tick later. Incident record, including the measured counts and the recovery: pandora run `.ai/runs/2026-09-11-memory-sync-wipe` (agent-tasks cda5b12c).
  - `run`'s pull-failure fallback no longer treats every git failure as "the remote is unavailable", which is what turned a broken pull into a push-only retry of an emptied workspace.
  - A pull never deletes a local file whose base snapshot is missing; such files are local-only and the run reports how many it protected.
  - A push whose plan deletes more than `massDeleteGuard.maxFiles` (default 20) or more than `massDeleteGuard.maxRatio` (default 10 percent) of a destination is refused (exit `5`) unless `--allow-mass-delete` is given, counted on the deletions the commit actually carries rather than on the ones the merge intended, plan-wide as well as per destination, and including paths outside `repositorySubdir`. The watcher's push obeys the same guard. The commit then carries the index exactly as measured (`GitClient.commitStaged`) instead of staging a second time on its way in, so a working copy wiped between the measurement and the commit can no longer be published.
  - A fetched working copy missing that much of what the base snapshot tracks is refused before any merge runs (exit `7`), on both the pull and the push side.
  - `run`, `watch` and `restore` take an advisory lock on the state directory (exit `8` when it is held), and `StateStore.clearTemp` clears only the caller's own working copy instead of the whole `tmp` root.
  - Before a pull deletes or overwrites anything in a destination, the destination's current tree is copied to `<stateDir>/snapshots/<destination>/<timestamp>/`, keeping `snapshotGenerations` (default 3).
  - A remote change that would delete more of a destination than the thresholds allow is not applied (exit `9`). `--accept-mass-delete` (on `run` only, one run at a time) applies it after the copy, and is the one override of the exit-`7` refusal: nothing at the file level tells a wiped working copy from a remote that genuinely dropped the files, and without an escape a legitimate large deletion wedges every mode permanently. `watch` does not take the flag, since on a long-running process it would be consent for every future tick. It cannot be combined with `--allow-mass-delete` (usage error, exit `2`), and `--dry-run --accept-mass-delete` reports the paths the real run would adopt without changing anything.
  - `restore <profile> <destination> --from-commit <sha>` and `--from-snapshot [<id>|latest]` bring a whole destination back and require `--yes` (`--dry-run` previews without it). A commit restore moves the base snapshot for that destination to the current remote tree, so the next push publishes the recovered files as additions. A restore source that is not there exits `10`, its own code, instead of sharing the refused-push code `5`.
  - New config keys: `massDeleteGuard`, `snapshotGenerations`, `lockStaleMs`.

### Changed

- **Breaking: `config get`'s exit contract changed.** `config get` of an unset key reused exit `5`, which now means only the push mass-delete guard. Found in round 4 of the 2026-09-11 wipe fix (pandora run `.ai/runs/2026-09-11-memory-sync-wipe`); pre-existing, outside that fix's scope. `config get <key>` on a supported key that is not currently persisted now exits `11`, its own documented code, instead of sharing `5`; a supported key with no value and an unsupported key are now distinguishable (`11` vs `3`) by exit code alone. A caller scripted against the old `5` on an unset key must switch to `11`.
- `watch --verbose` now prints `watch tick pushing snapshot` to stderr the instant a tick starts the git push work, instead of staying silent until the tick's result is known.
- `withTickDeadline` (test helper) gained an inactivity mode: it resets its deadline on either the ready line or the new push-start line, so a per-tick test budget bounds the gap since the last observed signal instead of the tick's total duration. A second, independent absolute cap (2.5x the inactivity budget) still bounds a tick that keeps signaling forever, failing with a distinct message.
- A pre-existing failure class under this package's documented load scenario stalls before either progress signal can fire: a chokidar filesystem-event delivery issue under CPU contention, present at the merge base too, at roughly a 30-40% failure rate under load on both. No timeout size fixes this; it is out of scope for this change and tracked as a follow-up.
- New unit tests in `tests/unit/watch-process-inactivity.test.ts` pin the inactivity and absolute-cap semantics directly, without a real spawn.
- Root-caused (but did not fix, see below) the follow-up above (agent-tasks f876dff6). Isolated outside chokidar entirely (a standalone script, no test harness), a bare `fs.watch()` on macOS can permanently miss a write issued <1ms after the watch is reported armed — Node's own documented, currently-unfixed behavior (nodejs/node#52601), not a chokidar bug; chokidar 4.x (this package's version) uses neither `fsevents` nor polling by default, so neither of that follow-up's original "polling vs fsevents" or "atomic-write visibility" candidates were actually in play. A second candidate mechanism — the parent test-runner process's own delayed reading of the child's stderr pipe under load — was measured and ruled out: p99 9ms / max 11ms across 600 samples under load, far too small to account for missing a 90s budget. Against this package's own documented 10-worker load scenario, the historical 30-40% stall did not reproduce: a 2026-08-16/17 measurement ran the scenario 5/5 green on the merge base, both idle and under load. No retry/workaround code was added as a result — the failure this task originally investigated is not currently reproducible, and speculative retry logic tried in an earlier iteration of this task was found on review to add a deterministic regression for no measurable benefit, so it was removed again. The one behavior change kept: `spawnWatch` (test helper) now spawns its child with stdout `'ignore'` instead of an unread `'pipe'`, since nothing reads it and an unread pipe backs up once the child writes past the OS pipe buffer (64KB), which would otherwise look exactly like an unexplained stall. See `tests/helpers/watch-process.ts`'s header comment and `src/commands/watch.ts`'s ready-line comment for the full measurement notes.
