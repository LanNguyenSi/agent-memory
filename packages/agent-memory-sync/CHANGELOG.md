# Changelog

All notable changes to `agent-memory-sync` are recorded here. This is a
private, internal-only tool (not published to npm; see `package.json`), so
there is no semver release process to anchor entries to — each entry below
is dated instead. The format is loosely based on
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Changed

- `watch --verbose` now prints `watch tick pushing snapshot` to stderr the instant a tick starts `performPush` (fetch/merge/commit/push), not only once the tick's result is known. Structural follow-up to PR #102, which raised `tests/helpers/watch-process.ts`'s per-tick test deadline to a honestly-documented 90000ms MARGIN (not a guarantee) after measuring that no fixed whole-tick budget can categorically rule out a CPU-contention straggler. `withTickDeadline` now has two modes: unchanged fixed-wall-clock behavior when called without a stderr source (`tests/integration/watch-teardown-guard.test.ts`'s deliberate never-resolving-`fn` case), and a new inactivity mode — used by `runWatchTick` and the two direct offline/online callers in `tests/integration/watch-mirror-delete.test.ts` — that resets its deadline on either the existing "watching N path(s) under ..." ready line or this new push-start line, so the budget bounds the gap since the last observed progress signal instead of the tick's total duration. `INACTIVITY_TIMEOUT_MS` is kept at 90000ms: an attempt to lower it to 45000ms was measured, not assumed, to be insufficient (failed on an ordinary local `npm test` run with no synthetic load, because the ready -> push-start gap turned out to be just as CPU-contention-sensitive as the git-work gap), and a separate attempt to raise it to 150000ms, specifically to chase a clean 10/10 under the load scenario below, made the pass rate WORSE (8/10, not better) — evidence that the residual failures are driven by this machine's ambient load, not by the budget's size; see `tests/helpers/watch-process.ts`'s `INACTIVITY_TIMEOUT_MS` comment for the full four-trial calibration history. A SIGSTOP'd child still fails reliably (this file's original reason for existing) well under this package's CI job's 10-minute timeout, verified at both 90000ms and 150000ms. Load-scenario evidence under PR #102's own scenario (10 concurrent `yes >/dev/null` workers racing `watch-restore.test.ts`, `watch-mirror-delete.test.ts`, and `watch-teardown-guard.test.ts` x10), measured honestly rather than cherry-picked: 27/30 (90%) across three independent 10-run trials at 90000ms, run back to back on this shared dev machine while its own ambient load (other concurrent agent sessions, per AGENTS.md) climbed from a load average of 14.34 to 20.11 on 12 logical cores over the course of the calibration session — confirmed to be an environmental effect, not a regression, by reproducing the identical failure class on unmodified origin/master via `git stash` at comparable ambient load. See agent-tasks eb798875-6355-413f-b274-91ba5a856b13's final report for the full quoted run-by-run history and the explicit recommendation surfaced to the orchestrator. New pinning tests in `tests/unit/watch-process-inactivity.test.ts` exercise `withTickDeadline`'s inactivity semantics directly (fast, no real spawn, deterministic): a slow-but-progressing tick that outlives one budget window in total but keeps signaling inside it must resolve, and a tick with zero progress signals must still be killed once the budget elapses.
