## [Unreleased]

### Added

- Score-blend resolver (mm-v1-T004): replaces the "shadowed gates" resolver (sync topic/tool gates first, the async Confidence Gate only when they stayed silent) with a single blend. That shadowing meant the Topic Gate's flat `1.0` score pre-empted the semantic path on almost every real prompt — three different prompts sharing a topic keyword produced an identical top-5 regardless of what each prompt actually meant, confirmed by a pre-change golden-set baseline run. New `resolveBlended()` in `src/router.ts` combines: a semantic score (the dominant signal, sqlite-vec cosine similarity, runs unconditionally whenever an index + embedding provider are available for the corpus, no longer gated behind the deterministic signals staying silent), a Topic Gate boost (no longer a standalone full-score hit), and small recency (file-mtime exponential decay) and type (`feedback` weighted highest) tie-breaking modifiers. A memory with neither a semantic score nor a topic match is excluded — the modifiers alone can never surface an otherwise-silent memory. Weights are overridable via the `MEMORY_ROUTER_BLEND_*` env namespace (`_TOPIC_BOOST`, `_RECENCY_WEIGHT`, `_RECENCY_HALFLIFE_DAYS`, `_TYPE_WEIGHT`, see `src/gates/confidence.ts`); the built-in defaults are explicitly documented as UNCALIBRATED pending a rollout measurement (mm-v1-T008) — this change does not tune them. A semantic-search failure is caught inside `resolveBlended` itself (degrades to topic/recency/type-only scoring) with an outer defensive try/catch preserved in every caller, same fail-open contract as before; the hook/MCP/eval callers never block a prompt over a resolution failure. `resolve()`, `resolveConfidence()`, and `dedupeAndRank()` in `src/router.ts` are unchanged (still relied on verbatim by `src/cli.ts`'s `test --semantic` verb and `src/hooks/pre-tool-use.ts`, both out of scope for this change) — `resolveBlended` is purely additive.

  Callers retargeted at the single new resolver: `src/hooks/user-prompt-submit.ts` (drops the `if (syncHits.length === 0)` shadowing, now threads `ctx.memoryDir` explicitly instead of relying only on the `MEMORY_ROUTER_DIR` env var), `src/mcp/server.ts`'s `memory_resolve` (no longer forks its own resolve-then-maybe-resolveConfidence logic — same blend path as the hook; `memory_search` is unchanged, it's a deliberately raw semantic-only tool), and `src/eval/runner.ts`'s `promptToHits` (now a single-line delegation to `resolveBlended`, wrapped in the same defensive try/catch as the hook; the `PromptToHitsDeps` test seam narrowed from `{resolve, resolveConfidence, dedupeAndRank}` to `{resolveBlended}`).

  New `tests/blend.test.ts` (16 tests): ranking (semantic score dominates a tie, topic match boosts without overriding a strong semantic lead, recency and type break ties at equal semantic+topic status), the "identical top-5" regression symptom (two prompts sharing one topic but different semantic content now rank differently), degradation without an index/provider (pinned identical memory-id selection to the old topic-only sync path via `resolve(ctx, memories, {gates:[topicGate]})`, using the real `semanticSearch` — no deps override), a semantic-search failure degrading to topic/recency/type-only hits rather than throwing, a memory with neither signal never surfacing, `ctx.tool` still resolving via the deterministic Tool Gate unaffected by the blend, invalid/non-positive env weight overrides falling back to the built-in defaults instead of producing `NaN` or dividing by zero, and two "exactly one embedding call per prompt" guarantees (a deps-seam call-count of `deps.semanticSearch` itself, since the real `semanticSearch`'s own query-embedding cache would silently mask a double-*call* at the HTTP layer — a repeat call with the same prompt+model is a cache hit, not a second request — plus a real-pipeline `stubFetch` HTTP-call-count check mirroring `tests/query-cache.test.ts`'s pattern). Rewrote `tests/eval-runner.test.ts`'s `promptToHits` seam-pinning tests for the new one-call shape with the same rigor as before (exact argument list `(ctx, memories, dir)`, no opts object; exactly one call into `deps.resolveBlended`; the result passed through unchanged, no re-ranking; degrades to `[]` rather than propagating when the dependency throws unexpectedly). Extended `tests/hooks.test.ts` (the rendered topic hit's score is no longer a flat `1.00`) and `tests/mcp-server.test.ts` (`memory_resolve`'s topic hit is a blended, non-`1` score in `(0, 1)`, proving it shares the hook's resolver rather than forking its own). Every new/changed assertion was verified by mutation, not just by reverting: a "topic-only hits regress to a flat 1.0" mutation in `resolveBlended` was caught by 5 tests across `tests/blend.test.ts`/`tests/hooks.test.ts`/`tests/mcp-server.test.ts`; a "call `resolveBlended` with an extra opts argument" mutation in `promptToHits` was caught by its dedicated argument-list test; a "call the embedder twice per prompt" mutation in `resolveBlended` was caught by the deps-seam call-count test (and, tellingly, was NOT caught by the fetch-count test alone, which is why both exist). Full suite (372 tests), `npm run typecheck`, and `npm run test:coverage` (97.27% lines / 88.13% branches / 89.73% functions, gate is 90/80/80 aggregate) all pass. README "How it works", the MCP `memory_resolve` tool table entry, "Try it in 60 seconds" / "What a run looks like" (regenerated against the real quickstart output — the topic-only score is now `0.23`, not `1.00`, and the semantic path's "embedding index missing" stderr warning now fires on every prompt, not only ones the deterministic gates missed), "Golden-set eval" → "What gets measured" (the semantic call is no longer conditional on the sync gates staying silent — this also changes the cost/latency profile of `eval` against a configured provider, called out explicitly), and the Status section are all updated to describe the blend instead of the old shadowed-gates resolver.

  Baseline discipline: a golden-set baseline (`P=0.100 R=0.167 MRR=0.375` on the sync-only path) was captured before this change; the orchestrator re-measures the same golden set after this change lands, and the sync-only (no index/provider) path is required to reproduce those exact numbers (the degradation pin above is the unit-level guarantee for that).

  Post-hoc fix (same task): the orchestrator's real-corpus re-measurement (289 memories, no index/provider configured) found the sync-only path had regressed against the baseline above (`P=0.050 R=0.083 MRR=0.050`, against the `P=0.100 R=0.167 MRR=0.375` baseline). Root cause: `resolveBlended` was still applying the topicBoost/recency/type modifiers even when the semantic path contributed nothing at all, which re-ranks (and on a corpus with more topic candidates than `maxHits`, can evict) the flat load-order top-N the old sync-only path selected; the original degradation-pinning test's 4-file shared fixture never had more than `maxHits` topic candidates for one prompt, so it never exposed this. Fix: `resolveBlended` now returns `resolve(ctx, memories, {maxHits})` verbatim whenever `semanticSearch` yields zero hits (no index/provider, or a caught runtime error), applying no topic boost and no recency/type modifier in that case. Blend scoring (semantic score + topic boost + recency/type) now runs only when the semantic path actually contributed a hit; the semantically-active path itself is otherwise unchanged. Hardened `tests/blend.test.ts`'s degradation-pinning test with a 7-memory single-prompt fixture (all sharing one topic, mtimes spread 0-120 days apart, all four `type`s represented, deliberately more than `maxHits`), asserting full `deepEqual` against `resolve()` (ids, scores, reasons, order), not just same-membership; also flipped the semantic-search-failure test and `tests/hooks.test.ts` / `tests/mcp-server.test.ts`'s degraded-mode assertions, which had pinned the blended (buggy) score as the intended contract, to the flat `1.0`/`1.00` contract instead. Verified by mutation, not just by reverting: disabling the new guard turned 4 tests red (both updated `tests/blend.test.ts` tests plus the `tests/hooks.test.ts` / `tests/mcp-server.test.ts` ones), file restored byte-identical (checksum-verified) before re-running green. README ("How it works" degradation sentence, the "Try it in 60 seconds" worked example, whose degraded score reverts from the blended `0.23` back to the flat `1.00`, and the Status section) updated to match. Full suite (372 tests), `npm run typecheck`, and `npm run test:coverage` (97.24% lines / 87.77% branches / 89.73% functions, gate 90/80/80) all pass.   Fix-round 2 (same task, review of the two entries above; 1 HIGH, 5 MEDIUM, 4 LOW): **HIGH** — a relevance floor: a semantic-search hit scoring below `MEMORY_ROUTER_BLEND_MIN_SEMANTIC` (default 0.5, the lower edge of the old `confidenceThreshold()` band, UNCALIBRATED pending mm-v1-T008 like every other blend weight) is now dropped in `resolveBlended` BEFORE the degradation guard, not blended in at a near-zero weight; a prompt whose only semantic "matches" are all sub-floor degrades to the deterministic topic-only path exactly as if the semantic path had found nothing. **MEDIUM** — a deterministic Tool-Gate hit (flat `1.0`) is now privileged into the final `maxHits` cap ahead of blend-scored memories via a new `rankWithToolPrivilege` (`src/router.ts`): since a blended score (semantic + topic boost + modifiers) can exceed `1.0`, plain highest-score-wins slot allocation could otherwise evict a real tool match on a prompt with more than `maxHits` strong blend candidates; attribution (which gate/score/reason wins for a memory present in both the blend and the tool hits) is unchanged, only slot allocation. **MEDIUM** — hardened five `tests/blend.test.ts` assertions the review found inert (passed regardless of the behavior under test): the ctx.tool passthrough test now runs against an ACTIVE blend (a non-empty semantic score elsewhere) instead of the degraded path, so it actually exercises the new privileged-slot code above; the `MEMORY_ROUTER_BLEND_TOPIC_BOOST` non-numeric-fallback and `MEMORY_ROUTER_BLEND_RECENCY_HALFLIFE_DAYS` non-positive-fallback tests now assert an exact computed score (against hardcoded, independent constants, not by calling the functions under test) instead of "some finite positive number" — the half-life test also backdates its fixture's mtime by the default half-life so the guard's effect is numerically measurable (at age 0 every half-life value produces the same decay, masking the guard entirely); the type-modifier tie-break test now reverses memory insertion order and asserts the exact score gap, so it no longer depends on `Array.prototype.sort`'s stability silently preserving a still-correct-looking ordering when the modifier itself is broken; README's "How it works" table/paragraphs, the "Try it in 60 seconds" negative-prompt example, and the `UserPromptSubmit` hook wiring section now state the relevance floor's role in keeping an unrelated prompt's stdout empty once an index exists, plus a cost/privacy note that every prompt reaches the embeddings endpoint once an index + provider are configured (OpenAI API cost / local Ollama load; disable by deleting the index). **LOW** — `MEMORY_ROUTER_BLEND_CANDIDATE_K` (default 10, UNCALIBRATED like the other weights) makes the semantic candidate-pool width (`Math.max(maxHits, candidateK)`, previously a hardcoded `10`) env-overridable. **LOW** — `envFloat` (`src/gates/confidence.ts`) now rejects a negative override for every `MEMORY_ROUTER_BLEND_*` knob, not just the half-life's existing non-positive guard, falling back to the built-in default instead (a negative boost/weight/floor/candidate-count would invert the blend's shape, not merely rescale it). **LOW** — `src/index.ts` (the programmatic entry point) now exports `resolveBlended`, which it had been missing since the first mm-v1-T004 entry above. **LOW** — `memory-router eval`'s report gained `semanticContributedCount`: how many of the golden set's prompts had at least one hit actually won by the semantic/confidence gate (a floor-clearing score that beat the other candidates), distinct from `semanticPathActive` (which only proves an index + provider are configured) — printed as `semantic contributed: N/M prompts` in the text report, additive in `--json`, documented in README "Golden-set eval". **LOW** — the blend's `gate`/`reason` attribution for a candidate is now derived from whether it has a `semanticById` entry at all, not from `score > 0`: with `MEMORY_ROUTER_BLEND_MIN_SEMANTIC` overridden down to `0`, a genuine zero-score semantic hit with no topic match used to be mislabeled `gate: 'topic'` with an empty `reason` (a phantom topic hit); it is now correctly labeled `gate: 'confidence'` with a `semantic match (score=0.00)` reason. Structurally unreachable under the default floor (`0.5`), reachable only via that explicit override.

- Multi-provider embeddings (mm-v1-T003): the Confidence Gate's embedder is now configurable via `MEMORY_ROUTER_EMBED_PROVIDER=openai|ollama` (explicit choice wins), otherwise auto-detects: `OPENAI_API_KEY` present → OpenAI, otherwise → a local Ollama daemon (`http://localhost:11434`, overridable via `MEMORY_ROUTER_OLLAMA_BASE_URL`), queried through its OpenAI-compatible `/v1/embeddings` endpoint with no auth, default model `nomic-embed-text`. `MEMORY_ROUTER_EMBED_MODEL` overrides the model for whichever provider is active. This lets the semantic path work on a machine with no OpenAI key. See README "Embedding provider" for the full matrix. `src/embed/provider.ts`'s `resolveProviderConfig()` gained a `ProviderConfig.provider` field and an opt-in `{ autoDetectOllama: true }` option (default off) so the function's synchronous, no-argument contract stays byte-identical for its two pre-existing callsites outside `embed/` (`src/lint/conflicts.ts`, `src/eval/runner.ts`, both untouched, both proven unmodified by their own test suites); only `src/embed/indexer.ts`'s `rebuildIndex`/`semanticSearch` opt in. `src/embed/index-store.ts` now records `provider`/`model`/`dimensions` provenance for an index (in the existing generic `meta` key/value table, no schema/migration change) and derives dimensionality from the first real embed response instead of a hardcoded constant; `semanticSearch`/`memory-router index` against an index built under a different provider (or, rarely, a different dimensionality under the same provider) now throw a clear error naming the exact rebuild command (`rm -rf <dir>/.memory-router && memory-router index <dir>`) instead of risking a silently-wrong-neighbours comparison. Switching `MEMORY_ROUTER_EMBED_MODEL` between two models of the *same* provider is deliberately unaffected by this check; the pre-existing per-row model tag already excludes stale rows from a search (unchanged, still exercised by `tests/query-cache.test.ts`). New `tests/embed-multi-provider.test.ts` (15 tests: explicit/auto-detect provider resolution, the sync contract, mocked OpenAI- and Ollama-shaped `embedBatch` request/response contracts, dimension-derived-from-first-response, and the provider-switch mismatch throw with the exact rebuild command) plus 2 tests in `tests/indexer-failopen.test.ts` retargeted at the narrowed null case (explicit `MEMORY_ROUTER_EMBED_PROVIDER=openai` with no key, since plain "no `OPENAI_API_KEY`" no longer implies "no provider" by itself once Ollama auto-detect is in play). No live network calls in any new/changed test. Full suite (338 tests) and `npm run typecheck`/`npm run build` pass; `tests/lint-conflicts.test.ts` and `tests/eval-runner.test.ts` pass unmodified.

- `memory-router eval <golden.yml> [--dir <path>] [--json]`: golden-set precision/recall/MRR baseline measurement against a labelled `(prompt, expected memory ids)` set, mirroring exactly what the `UserPromptSubmit` hook would select per prompt. A report, not a gate: no threshold/exit-code contract on the metrics; exits 0 on any error-free run. `--json` emits a stable, documented schema including `unknownExpectIds` (golden ids that don't resolve against the loaded corpus). See README "Golden-set eval".
- `<MEMORY_ROUTER_DIR>/topics.yml` corpus-controlled topic vocabulary (mm-v1-T002): the Topic Gate and `lint --unknown-topics` no longer work against a closed, in-package 5-topic union. A `topics.yml` file (top-level list of `{ name, description?, patterns? }` entries) at the root of the memory dir overrides the built-in default (`deployment`, `destructive_ops`, `workflow`, `security`, `testing`) corpus-wide; a missing file falls back to the built-in default, unchanged. New `src/vocab/loader.ts` validates `name` (required, unique) and `patterns` (optional regex strings): a single non-compiling pattern, or a topic declared with no patterns at all, degrades to a keyword match on its own `name` instead of dropping the topic or crashing the loader. An invalid `topics.yml` (YAML error, missing/duplicate `name`, wrong field shape) is rejected with a clear message; the Topic Gate always falls back to the built-in default and never crashes (the `UserPromptSubmit` hook must never block a prompt), and `lint --unknown-topics` also falls back for its scan but surfaces the rejection reason at the top of its report via the new `LintReport.vocabularyError` field. `Topic` is now a plain `string` at the type level rather than a closed union; validity is resolved at load time against whichever vocabulary is active. `src/tag/heuristics.ts` (the offline `tag` CLI) is unchanged and stays on the built-in default only, out of scope for this change; see README "Topic vocabulary" for the resulting gate/lint-vs-tag inconsistency when a corpus overrides the vocabulary. New `tests/vocab-loader.test.ts` plus extended `tests/topic.test.ts` / `tests/lint-topics.test.ts` cover custom-vocabulary load/match, missing/broken-file fallback, duplicate/missing-field rejection, and single-bad-pattern degradation: 26 new/extended tests across these three files, of which 24 fail against the pre-change source (confirmed by reverting `src/vocab/loader.ts`, `src/gates/topic.ts`, and `src/lint/topics.ts` to their pre-mm-v1-T002 state and re-running); the remaining 2 (`tests/topic.test.ts`'s "$MEMORY_ROUTER_DIR set but no topics.yml present: built-in default still applies" and "broken topics.yml at $MEMORY_ROUTER_DIR: gate never throws, falls back to built-in default") are deliberate unchanged-behavior guards whose assertions hold before and after this change by construction (the pre-change gate never consulted `topics.yml` at all, so "no topics.yml" and "broken topics.yml" both trivially degrade to the built-in default either way); a plain revert would not turn them red, so they were verified by mutation (temporarily breaking the fallback path and confirming the test catches it) instead. Example vocabulary at `tests/fixtures/vocab/topics.yml`. The real Pandora corpus vocabulary is not part of this change, it lands with the corpus rollout. A review-round-2 fix-up landed on top of this entry (dir-threading the corpus dir via `ctx.memoryDir` instead of only the `MEMORY_ROUTER_DIR` env var, a ReDoS safety screen on `topics.yml` patterns, `name:` trimming and a lookaround-based keyword-fallback boundary for punctuation-leading/trailing topic names, and test-suite hermeticity against an ambient `MEMORY_ROUTER_DIR`); 323 tests in the full suite as of that fix-up, all pass identically whether or not `$MEMORY_ROUTER_DIR` is set ambient to an unrelated corpus; `npm run typecheck` clean.

## [0.3.0] - 2026-05-15

### Added

- `memory-router-user-prompt-submit --version` (alias `-v`): fast-exit CLI short-circuit that prints the package version and returns 0 before touching stdin. Tooling that probes installed memory routers (e.g. `harness doctor`'s `memory.router.min_version` check in harness 0.13) otherwise hangs on `readStdin()` until the 5s probe budget expires. A new node:test in `tests/cli-version.test.ts` reads `package.json#version` and asserts the bin's stdout matches, catching drift if the in-source `PACKAGE_VERSION` constant gets out of sync with `package.json` on a release bump.

### Fixed

- Build now restores `+x` on the four `bin` targets (`memory-router`, `memory-router-user-prompt-submit`, `memory-router-pre-tool-use`, `memory-router-mcp`) via a postbuild `scripts/chmod-bins.mjs` step. `tsc` strips the execute bit on its JS output, and `npm link` (unlike registry installs) does not chmod link targets, so every rebuild used to leave the hooks failing with "Permission denied" until manually fixed.

## [0.2.0] - 2026-05-05

### Added

- `lint --conflicts --semantic` (#30): embedding-cosine upgrade for paraphrased opposite-polarity pairs the regex pass misses ("always squash before merge" vs "never squash, use fast-forward only"). Reuses the live `index.sqlite` when available; embeds misses on the fly without persisting. Fail-open with a stderr warning when `OPENAI_API_KEY` is unset, so CI without secrets stays green.
- `lint --conflicts --json` (#32): machine-readable report mirroring the `--drift --json` contract. Schema: `{ scannedCount, feedbackCount, hits: [{ severity, topic, reason, a, b }] }`. When combined with `--drift --json`, drift owns stdout and conflicts routes to stderr so a single CI step can pipe both fds.
- Extended polarity vocabulary (#32): formal-register markers `mandatory`, `mandate`, `compulsory`, `prohibit`, `forbid`, `disallow`, `cannot` (plus inflections), so memories written without `ALWAYS`/`NEVER` still classify and still get filtered out of subject-token Jaccard.
- `stale --repo-root <p>` repeated, and variadic `stale --repo-roots <p1> <p2> ...` (#33): multi-repo workspace mode for the stale linter. A ref is STALE only when none of the roots resolves it; first hit wins. The single-root detail format is preserved for v1 CI scrapers; multi-root emits a single-line aggregated summary. `symbolCheckDegraded` is `true` only when every probed root is non-git.
- Date-staleness pass (#34): every memory whose newest ISO date in the body is more than 90 days old AND whose frontmatter has no newer `updatedAt:` is flagged `possibly-stale`. INFO-only, never blocks CI.
- `stale --check-urls` (#34): HEAD-request every external URL extracted from the body. `4xx` → STALE; `5xx` and network errors → `skipped`; `2xx`/`3xx`-following → silent. 5-second timeout. Off by default because it's network-dependent.

### Changed

- Polarity detection scope (#31): lowercase markers (`always`, `never`, `prefer`, `avoid`, ...) now only fire against the first two whitespace-separated tokens of the line; ALL-CAPS variants still match anywhere. Mixed polarity is still detected when a leading directive is contradicted later on the line. The Jaccard subject-overlap floor was lowered from `0.25` to `0.15` now that descriptive mid-sentence false positives are filtered upstream.
- Debug stderr prefix unified to `[memory-router]` (#29): both the loader's rejection warnings and the indexer's query-cache observability share one bracketed prefix; `grep '^\[memory-router\]'` now catches every gated diagnostic.

### Schema

- v1 → v2 migration (#35): adds `model TEXT` column to the `entries` table. Embeddings are now stamped with the producing model so `semanticSearch` (Confidence Gate) and `lint --conflicts --semantic` cannot silently mix vectors from incompatible embedding spaces. The migration is idempotent (PRAGMA `table_info` probe before `ALTER`), so opening a 0.1.x index file just adds the column; pre-v2 rows survive with NULL model. The next `semanticSearch` open emits a one-line stderr warning recommending `memory-router index <dir>` to refresh; once rebuilt, every row carries the active `MEMORY_ROUTER_EMBED_MODEL`.

### Compatibility

- API change: `IndexStore.upsert(id, mtime, embedding)` is now `upsert(id, mtime, model, embedding)`. `getEmbedding(id, expectedModel?)` and `search(query, k, expectedModel?)` accept an optional model filter that rejects cross-model rows (and pre-v2 NULL rows). Direct programmatic callers of `IndexStore` need to pass a model name; hook / CLI / MCP users see no behaviour change beyond the upgrade-path warning above.

## [0.1.0] - 2026-05-05

First public release.

### Added

- **Three-gate router**: deterministic memory injection for Claude Code, gated by topic dictionary, tool-call regex, or a fallback ambiguity-driven semantic match.
- **Hook binaries**: `memory-router-user-prompt-submit` and `memory-router-pre-tool-use` consume Claude Code's hook stdin contract and emit `hookSpecificOutput.additionalContext` on stdout.
- **MCP server** (`memory-router-mcp`) exposing `memory_search`, `memory_resolve`, and `memory_apply` for imperative checks.
- **CLI** (`memory-router`) with subcommands:
  - `tag` to propose `topics:` / `severity:` frontmatter for legacy memories.
  - `index` to build a sqlite-vec embedding index, including an LRU query-embedding cache.
  - `lint` with three checks: `--drift` (MEMORY.md vs. on-disk corpus), `--unknown-topics` (typos against the topic registry), `--conflicts` (opt-in: pairs of feedback memories with topic overlap and opposite-imperative directives).
  - `stale` to flag broken path / symbol references in memory bodies. `verify:`-frontmatter-only by default; `--scan-body` opts in to body-regex extraction.
- **Schema-versioned sqlite index**: `meta.schema_version` row + migration framework, so future on-disk shape changes have a clean upgrade path.
- **Frontmatter `verify:` contract**: memories declare claims about the repo state. The runtime side prefixes a stale warning when the claim no longer holds; `memory-router stale` checks the same claims proactively.
- **Observability**: `MEMORY_ROUTER_DEBUG=1` emits one stderr line per rejected memory file (broken YAML, missing required field, etc.) without touching stdout.

### Compatibility

- Node 22 or newer.
- Native dependencies: `better-sqlite3` and `sqlite-vec`. The CI smoke step verifies they load before tests run.
